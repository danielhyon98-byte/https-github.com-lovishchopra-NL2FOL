# Dossier guide

## 1. Scope

This document describes the dossier: the one JSON object you receive for one task. It applies to every dossier.

**It covers:**

- the header you copy into your verdict
- the fields of a transfer, a receipt, a result and the links
- the index, which gives you a ready pointer for every identifier
- how to build a JSON Pointer
- lenses and modes
- a translation and its formal problem
- consolidations of the answers several agents gave to one input (informed mode)
- the facts about the system you can rely on
- how the request's constraints are written from the student's words
- answers of the science, mathematics and computer science branches (STEM answers): their claims, translations, formal checks and ST codes

**It does not cover.** Other documents handle these:

- **Inspection:** what to check in these fields.
- **Evidence rule:** how pointers and quotes are used in an accusation.
- **Verdict format:** the output.

Rules marked **(enforced)** are checked by the infrastructure's code.

## 2. Quick reference

1. You may cite only what is in the dossier. **(enforced)**
2. Copy the header fields into your verdict exactly. **(enforced)**
3. Take pointers from `at` and from `index`; never compute a pointer from `seq`.
4. Arrays count from 0.
5. Quote only from the visible part of a truncated field. **(enforced)**
6. A link tells you where to look. It does not tell you that two things are equal.

## 3. The dossier at a glance

```
{
  "dossier_version": "1.0",
  "dossier_sha256": "<64 hex characters>",          copy into the verdict
  "verdict_contract": "overseer_verdict/1.0",        copy into the verdict as "contract"
  "agent_id": "<your agent id>",                      copy into the verdict
  "issue_binding": "<32 hex characters>",             do not copy: it only makes dossier_sha256 yours
  "pack": {"name": "...", "version": "...", "sha256": "..."},   copy into the verdict
  "mode": "blind" | "informed",
  "lens": "custody_results" | "content_fidelity" | "translation_fidelity" | "peer_synthesis" | "general",   copy into the verdict
  "task": {"task_id": "...", "request_id": "...", "plan": {...}},    copy task_id into the verdict
  "transfers": [ {...}, {...} ],                      every transfer, in the order issued
  "results": { "<result_id>": {...} },                engine results by id
  "links": { "forwards": [...], "peer_documents": [...], "synthesis_citations": [...], "translations": [...] },
  "index": [ {"type": "...", "id": "...", "pointer": "..."} ],
  "auditor": { "findings": [...] },                   informed mode only
  "consolidations": [ {...} ],                         informed mode only, when several agents answered one input
  "limits": { "truncated_fields": [...] }
}
```

## 4. The header

- **D1 One dossier, one task.** **(enforced)** The dossier covers one task. Cite only identifiers, fields and text that it contains.
- **D2 Copy the header.** **(enforced)** These six values go into your verdict unchanged, character for character:

| Dossier field | Verdict field |
| --- | --- |
| `verdict_contract` | `contract` |
| `pack` (the whole object: `name`, `version`, `sha256`) | `pack` |
| `agent_id` | `agent_id` |
| `task.task_id` | `task_id` |
| `dossier_sha256` | `dossier_sha256` |
| `lens` | `lens` |

  `issue_binding` is not copied. It is part of what `dossier_sha256` covers, so the digest you copy is yours alone.
- **D3 The plan.** `task.plan` is the router's plan: the task and subject, `selected_agent_ids` (the agents it chose), `allowed_document_ids` (the documents in scope; empty means unrestricted), `agent_subjects` (each agent's subject) and `agent_task_types` (each agent's task type).

## 5. Lenses

- **D4 Where to start.** Your `lens` tells you where to start:
  - `custody_results`: envelopes, receipts, engine results and formal checks.
  - `content_fidelity`: delivered claims against the response, quotations, figures and dates, and self-certifications.
  - `translation_fidelity`: the translations: each claim, the claims it cites, and the formal problem the translator proposed for it.
  - `peer_synthesis`: router forwards, peer documents, the combinator's ledger, and contradictions between claims.
  - `general`: all of the above.
- **D5 A lens never limits you.** Review every transfer. You may accuse anything you find, whatever your lens.

## 6. Modes

- **D6 Blind and informed.**
  - `blind`: you do not see the infrastructure's own audit findings. The `auditor` field is absent.
  - `informed`: `auditor.findings` lists the infrastructure's findings (codes starting `OVS-`). Do not accuse those again. Look for what they do not cover.
  - In informed mode, do not repeat the exact comparisons the checks make: payload and forward digests, peer documents word for word, quotations found or not found, figures and dates, word and paragraph counts, the status rule, and the translation checks (Inspection I71 to I77). When they find a fault, its `OVS-` code is in `auditor.findings`. Spend your review on what no check decides: whether a request says what the student asked (Inspection I13), self-certifications (Inspection I24), whether a translation says what its claim says (Inspection I78), consolidations (Inspection I84 to I87), and whether a synthesized claim keeps who acted and what was meant (Inspection I69).
  - In both modes the receipts' own findings (codes starting `INT-` and branch codes) are part of each transfer and are always shown.

## 7. A transfer

Each entry of `transfers` has these fields:

| Field | Content |
| --- | --- |
| `at` | This transfer's own pointer, for example `/transfers/3`. Build every pointer into this transfer from it. |
| `seq` | The order the transfer was issued in, starting at 1. Not the array position. |
| `kind` | `request`, `response`, `response_text`, `relay_forward`, `relay_report` or `relay_synthesis` (Inspection explains each). |
| `message_id`, `receipt_id` | The transfer's identifiers. |
| `direction` | `router_to_specialist`, `specialist_to_router` or `agent_to_agent`. |
| `sender`, `recipient` | Each has `agent_id` and `role` (`router`, `specialist`, `combinator`, ...). |
| `contract` | The payload's contract, for example `task_request/1.0`, `specialist_report/1.0`, `specialist_report_forward/1.0`, `synthesis/1.0`. |
| `in_reply_to` | The message this one answers, or null. |
| `created_at` | When the transfer's envelope was created (UTC). Order transfers by `seq`, never by this time. |
| `payload_sha256` | The digest of the payload as issued. Two transfers that carry the same payload have the same digest. |
| `payload` | The typed payload: a request, a specialist report, a forwarded report or a synthesis. For a withheld response it is `{"withheld": {"response_sha256", "response_chars"}}`: the text was refused and not parsed. |
| `raw_text` | For `response_text` only: the specialist's text exactly as received, when retained. |
| `receipt` | `status`, `findings`, `coverage`, `constraint_results`, `outcomes`, `structural_findings`, `formal_checks`, `formal_result_ids`, `summary`. |
| `cited_result_ids` | Every result id the receipt cites. |
| `pool_after` | The formalized claims pooled after this transfer: `claim_id`, `report_id`, `agent_id`, `problem_digest`, `ambiguous`. |

**The payloads you will meet.**

- A **request** (`task_request/1.0`): `to_agent_id`, `subject`, `task_type`, `user_input` (the student's words), `items` (what must be answered), `constraints` (limits such as word counts, each with `constraint_id`, `kind`, `value`, `text`), `supplied_texts` (documents, each with `document_id` and `text`).
- A **specialist report** (`specialist_report/1.0`, and `specialist_report_forward/1.0` when the router forwards one): `report_id`, `agent_id`, `original_response` (the specialist's text as received), `supplied_texts`, and `claims`. Each claim has `claim_id`, `claim_text`, `claim_role`, `materiality` (`material` or `supporting`), `certainty`, `source_refs` (each with `document_id`, `locator`, `excerpt`), and the self-report fields `advisory_verification_status` and `advisory_verification_eligibility`.
- A **synthesis** (`synthesis/1.0`): `synthesis_id`, `combinator_agent_id`, `source_report_ids`, `claims` (synthesized claims with `claim_id`, `text`, `certainty`, `materiality`, `source_claim_ids`, `transformation`, `formal_conclusion`), `ledger` (what happened to each source claim: `source_claim_ids`, `transformation`, `synthesized_claim_id`, `reason`), `conflicts` (contradictions the combinator named: `conflict_id`, `claim_ids`, `description`, `status`) and `text`.

**A receipt.**

- `status`: ACCEPTED, ACCEPTED_WITH_FINDINGS or REJECTED.
- `findings`: each has `code`, `severity` (`error`, `warning` or `info`), `message`, and the identifiers it names (`claim_ids`, `message_ids`, `report_ids`, `agent_ids`, `document_ids`, `formal_result_id`).
- `outcomes`: one per checked claim: `claim_id`, `translation` (what the translator proposed for the claim, with its `status`, `claim_id`, `claim_text_sha256` and `problem`; see §11), `verification` (the engine result as carried on the receipt, with its `result_id`, `status`, `premises_relied_on`, `ungrounded_dependencies` (relied-on premises the supplied material does not establish) and `unverified_dependencies` (relied-on premises whose grounding no procedure checked)), `display_status` (the status shown to the router) and `summary` (one plain statement of what was checked for that claim).
- `constraint_results` and `formal_checks`: each has `constraint_id`, `satisfied` (true, false or null), `method`, `detail`, `formal_result_id` and `formal_status`.
- `coverage`: each request item, whether it was `addressed`, and by which claim ids.
- `structural_findings`: findings of the subject branch's own deterministic checks.
- `summary`: one plain sentence of what happened. Every receipt except a request receipt ends with the sentence "Formal results concern only the encoded checks under their premises; coverage is heuristic."

## 8. Results, links, index, auditor, limits

- **D7 Results.** `results` maps each `result_id` to: `status`, `claim_id`, `request_id`, `problem_id`, `query`, `binding` (`problem_digest`, `config_digest`, `versions_digest`, `binding_digest`), `solver_config`, `premises_relied_on`, `ungrounded_dependencies`, `signature_present`, `signature_key_id`, and `problem` when retained. A result id cited on a receipt but missing from `results` is worth checking (Inspection I8).
- **D8 Links.** `links` helps you find related transfers:
  - `forwards`: each router forward with the `report_id` it carries and the `message_id` of the transfer that delivered that report.
  - `peer_documents`: each `peer:<task>` document in a request, with the earlier forwards to the same recipient.
  - `synthesis_citations`: each synthesis with the reports it cites and the transfers that delivered them.
  - `translations`: each translation the router received, with its `claim_id`, `report_id` and `message_id`, the `claim_pointer` of the claim it translates, the `cited_claim_pointers` of the claims that claim cites (what the translator was given with it), the `translation_pointer`, and the `result_id` of its engine result (null when the engine did not run).
  
  A link says where to look. It does not say that the two are equal, or that a translation is faithful. Compare them yourself.
- **D9 Index.** `index` lists every identifier in the dossier with a ready pointer. Each entry has `type` (`message`, `receipt`, `report`, `claim`, `synthesized_claim`, `result`, `document`, `conflict`), `id`, and `pointer`; a claim entry also has `report_id`, because two reports may use the same claim id. Use the index to find an identifier and to build pointers. Never guess an array position.
- **D10 Auditor.** In informed mode, `auditor.findings` holds the infrastructure's `OVS-*` findings. They are already decided. You may mention one in a statement; do not accuse it again.
- **D11 Limits.** String fields longer than 20,000 characters are shortened. `limits.truncated_fields` lists each shortened field's pointer, the digest of the full text and its length. **(enforced)** Quote only from the visible part.

## 9. Building a pointer

- **D12 JSON Pointer.** A pointer is a path into the dossier, starting with `/`, one step per key or array position. Arrays count from 0.
  - Start from a transfer's `at`, or from an `index` pointer.
  - Add the keys down to the field: `/transfers/3` + `/payload/claims/2/claim_text` gives `/transfers/3/payload/claims/2/claim_text`.
  - A result: `/results/<result_id>/status`.
  - If a key contains `/`, write it as `~1`; if it contains `~`, write it as `~0`.
- **D13 Never from seq.** `seq` starts at 1 and may skip; array positions start at 0. Never build `/transfers/N` from a `seq`. Use `at`.

## 10. Facts you can rely on

- **D14 Statuses.** A receipt status is ACCEPTED, ACCEPTED_WITH_FINDINGS or REJECTED. A REJECTED transfer was **not delivered**: nothing in it reached the recipient, the pool or any record.
- **D15 The response.** A report's `original_response` is the specialist's text as received. Every delivered claim should be carried by that text.
- **D16 Engine statuses.** Only six statuses are definitive: ENTAILED, COUNTEREXAMPLE, INCONSISTENT_PREMISES, CONSISTENT, SATISFIABLE and UNSATISFIABLE. None of them means a claim is true: each is a property of the encoded problem. Every other status (UNKNOWN, TIMEOUT, UNSUPPORTED, INVALID_FORMALIZATION, AMBIGUOUS_TRANSLATION, NOT_ELIGIBLE, INTERNAL_ERROR) is a non-result. COUNTEREXAMPLE on an entailment query means the encoded premises do not imply the encoded conclusion. It never means the claim is false, refuted or wrongly translated.
- **D17 Notes, not content.** A claim with `claim_role` `other` is a note (a label, a self-report, a task note), not content.
- **D18 Peer documents.** A supplied text named `peer:<task>` is a forwarded report's `original_response`, supplied to another specialist.
- **D19 Signatures.** You cannot verify signatures. You see only `signature_present` and `signature_key_id` (Role and trust T7).
- **D20 Claim ids.** A claim id is unique inside one report, never across reports. Each parser numbers the claims of an answer by paragraph and statement: the History parser `h1.6`, the generic parser `g4.2@economics-specialist` (the number qualified with the agent; recorded rounds of an earlier version write `g4.2`), and the science, mathematics and computer science parsers `s1.2`, `m1.2` and `c1.2`. Two agents of one branch number their answers the same way, so one id names a claim in each of their reports: always name the `report_id` with a claim id, and the `message_id` of its transfer. A claim whose id ends in tail (g.tail, h.tail, s.tail, m.tail or c.tail) holds the statements beyond the report's claim limit (INT-REQ-013).

## 11. Translations

- **D21 A translation.** Each outcome's `translation` is what the translator proposed for one claim:
  - `status`: TRANSLATED, AMBIGUOUS_TRANSLATION, NOT_ELIGIBLE, UNSUPPORTED, INVALID_FORMALIZATION or TRANSLATION_FAILED. Only TRANSLATED and AMBIGUOUS_TRANSLATION carry a `problem`, and only those are run by the engine.
  - `eligibility`: the infrastructure's policy decision about the claim: `eligibility_class`, `eligible` and `reasons`. A claim the policy rules out is never sent to the translator.
  - `problem`: the formal problem (D22).
  - `interpretation`: the translator's `reading` of the claim, its `glossary`, and its `ambiguity_flags`, each with `code`, `message` and `alternatives`: the readings it saw.
  - `grounding_checks`: the code's checks of quotations, and of a task-authority premise's numbers against the task material (`method` `numeric_in_task` or `relation_in_source`: a number match, no transcription, I77): `target_id`, `document_id`, `method`, `verified` (true, false or null) and `detail`.
  - `provider`: present, with its `provider_name`, when a model proposed the translation; absent when the policy ruled the claim out before any model was asked (NOT_ELIGIBLE). A problem with no `provider` is reported by the checks (OVS-TRN-002), unless the operator declared its translator hand-built.
  - `diagnostics`: why an earlier attempt failed, or why the status is not TRANSLATED. An INVALID_FORMALIZATION whose `diagnostics` name E112 is an encoding the translator withheld itself: a premise the writer supplied (an assumption, a specialist inference, general knowledge, an unchecked quotation or arithmetic fact) restated the conclusion, so the claim would have been proved from itself (Inspection I77). One whose `diagnostics` name stated precision encoded rounded figures as exact equalities. Neither was run by the engine. The translator does not withhold a restatement grounded `task_setting`, `supplied_text`, `rubric_rule`, `knowledge_document` or `library_source`: it reads the label as a transcription even when no check verified it, and delivers it. Nor does it withhold a premise that restates the conclusion in another form than its exact `expr` (Inspection I77).
- **D22 The formal problem.** A `problem` has:
  - `symbols`: each with `name`, `sort` (Bool, Int or Real), `meaning` (in words) and `grounding`;
  - `premises`: each with `id`, `expr`, `label` (the premise in words) and `grounding`;
  - `conclusion`: the same fields: the claim, encoded;
  - `query`: `entailment` asks whether the premises imply the conclusion; `consistency` whether the premises can all hold together; `satisfiability` whether some assignment makes every premise true (a STEM branch asks it of a Boolean identity's negation, D31).
  
  An `expr` is a tree of nodes, each with an `op`: `var` (a symbol, by `name`); the constants `bool`, `int` and `real` (in `value`); `not`; `and` and `or` (with `args`); `implies` and `iff` (with `left` and `right`); the arithmetic `add`, `sub`, `mul`, `neg`, `div`, `idiv` and `mod`; and the comparisons, each with `left` and `right`: `eq` (equal), `ne` (not equal), `lt` (less than), `le` (at most), `gt` (more than) and `ge` (at least).
  
  A `grounding` says where a symbol or assertion comes from: its `kind` (`quotation`, `supplied_text`, `task_setting`, `rubric_rule`, `arithmetic_fact`, `specialist_inference`, `assumption`, `knowledge_document`, `library_source` or `general_knowledge`), its `source_refs` (each with `document_id` and `excerpt`), its `certainty`, and `verified`, which only code sets: true when the excerpt was found in the named document, false when it was not, null when nothing could be checked.
- **D23 What a result says about a translation.** ENTAILED means the premises, as encoded, imply the conclusion, as encoded. It never means that the encoding says what the claim says, nor that the claim is true. COUNTEREXAMPLE means the premises, as encoded, do not imply the conclusion, as encoded. Often a part of the claim has no support in the report, and the translator left it without a premise to show that (a missing link, Inspection I81). It never means that the claim is false or refuted, nor that the translation is wrong. An AMBIGUOUS_TRANSLATION is displayed as AMBIGUOUS_TRANSLATION whatever the engine found. A result whose `diagnostics` name E108 (vacuous: no premise used), E110 (a figure defined but never asserted), E111 (the claim's own reason not encoded) or E112 (a proof whose premises restate the conclusion) is displayed INVALID_FORMALIZATION: the engine's status is no verdict on the claim (Inspection I26).

## 12. Consolidations

- **D24 When there are consolidations.** `consolidations` appears only in informed mode, and only when several agents answered one input (Role and trust T14). Each entry is the infrastructure's signed consolidated response for one input. Its own pointer is `at` (for example `/consolidations/0`). Build every pointer into it from `at`. It copies no agent text: it names transfers by `message_id` and points at them with `transfer_pointer`.
- **D25 A consolidation.** Each entry has:
  - `consolidation_id`, and `signature_present`;
  - `status`: CONSOLIDATED (one group, a clean representative, nothing excluded), CONSOLIDATED_WITH_FINDINGS (one group, with something excluded, repeated or not clean), CONFLICTING (two or more groups, or a conflict: no answer is chosen) or NO_DELIVERABLE_OUTPUT (every answer excluded);
  - `user_input_sha256` (the input) and `request_message_ids` (the requests that carried it);
  - `deliverable_message_id`: the one answer the router may deliver, or null; it is null unless the status is CONSOLIDATED or CONSOLIDATED_WITH_FINDINGS;
  - `groups`, `excluded`, `repeats`, `conflicts` and `advisory` (D26, D27).
- **D26 Groups.** A group holds answers the infrastructure found to be the same. It has `group_id`, `basis`, `members`, `canonical_message_id`, `canonical_clean` and `merge_check`.
  - `basis` is `single` (one answer), `identical_text` (the same `original_response`, apart from the typographic differences of Inspection I9) or `same_material_claims` (other wording, but the same material claims with the same figures, dates and quotations, and a `merge_check` whose `relation` is `consistent`: the engine found their encodings consistent with each other).
  - Each of the `members` has `message_id`, `agent_id`, `transfer_pointer` (the pointer of its transfer), `clean` (true when its receipt is ACCEPTED and nothing names it, or when its only receipt findings are INT-REQ-016 warnings that name other answers to the same input: duplicated instances number their claims alike) and `finding_codes`.
  - `canonical_message_id` is the representative: the earliest clean member. When no member is clean, it is the earliest member, and `canonical_clean` is false.
- **D27 Excluded answers, repeats, conflicts and advisory notes.**
  - `excluded`: each answer kept out of every group, with `message_id`, `agent_id`, `transfer_pointer`, `codes` (the error codes that exclude it), `result_ids` (the signed results those findings cite), `repeated` and `reasons`.
  - `repeats`: each repeated fault: its `code`, the answer that repeats it (`message_id`, `agent_id`, `transfer_pointer`), the earlier answer it repeats (`first_message_id`, `first_agent_id`, `first_transfer_pointer`), `occurrence` (2 for the first repeat) and `same_agent` (true when the same agent resubmitted it). A repeated fault is the same kind of fault, about the same quoted words or the same claim words, with the same figures, as in an earlier answer of the task. `repeats` lists only error-level faults: an error finding on an answer's receipt, or an error-level `OVS-FID` or `OVS-TRN` finding naming the answer. A warning that recurs across answers (a paragraph count, a structure warning) is never listed.
  - `conflicts`: groups that cannot be reduced to one answer: `group_ids`, `excluded_message_id` (an excluded answer that contradicts a group), `relation` (`contradiction`, `consistent`, `undecided` or `not_checked`) and `check` (the engine run behind the relation).
  - `advisory`: answers that look the same that the engine could not confirm. They stay in separate groups and are never merged.

## 13. The request's constraints

- **D28 How constraints are written.** The infrastructure writes each request's `constraints` from the student's words by fixed rules. The constraint's `text` keeps the student's words; its `kind` and `value` follow these rules:
  - "about", "around" or "approximately" N words: `min_words` N minus 10 per cent, rounded up, and `max_words` N plus 10 per cent, rounded down ("about 250 words" gives 225 and 275). The student's number is a target, so the bound has a margin on both sides.
  - "in" N words: `max_words` N plus 10 per cent, rounded down ("in 350 words" gives 385).
  - "no more than", "at most", "maximum of", "up to", "under" or "within" N words: `max_words` N.
  - "at least" or "minimum of" N words: `min_words` N.
  - "exactly" N words: `min_words` N and `max_words` N. "Between" A and B words: `min_words` A and `max_words` B.
  - "no more than" or "at most" N paragraphs: `max_paragraphs` N. "At least" N paragraphs: `min_paragraphs` N. "In", "write", "give" or "exactly" N paragraphs ("one paragraph", "a single paragraph"): `min_paragraphs` N and `max_paragraphs` N.
  - "quote", "quotations", "cite" or "textual evidence": `must_cite_supplied_text`.
  - Words right after a word bound that set something outside it ("plus working", "excluding calculations", "not counting your diagram") are listed in the constraint's `excludes` ("working", "diagram"): the words of that part are not counted.
  - On a science, mathematics or computer science answer, a displayed formula and a code block each count as one word.
  - When one span states a minimum and a maximum ("about 250 words", "between 300 and 400 words") and the count lies within both, one formal problem decides both: its conclusion `BOUND` is an `and` of a `ge` and a `le`, and both constraints cite its result. A count outside them is decided bound by bound.
  A value these rules give from the constraint's own `text` is not a miscommunication (Inspection I13).

## 14. STEM answers

- **D29 A STEM answer.** An answer routed to a science, mathematics or computer science specialist is read statement by statement. Each claim is one statement exactly as the answer writes it, never rewritten: a sentence, a line of working, a row of displayed mathematics, a list item, a code block, a table or a data line. A statement of mathematics may hold no words at all ("√8 = 2√2"). Its `claim_role` says what the statement does:
  - a heading with nothing of its own ("Given:", "Working:"): `structural`;
  - a given value, a law or formula, a table or a data line: `evidence`;
  - a substitution, a calculation or an algebra step: `quantitative`; the last step of each part, its result, is `material`;
  - a code block: a `material` `point`;
  - a sentence of explanation: `point`, `link` or `analysis`;
  - a note or a self-certification: `other` (D17).
- **D30 A STEM translation.** Two things hold for every translation, because the code enforces them: each number in the IR is an exact integer, fraction (`a/b`) or decimal, written with no exponent (the IR admits no other numeral, so 6.67 × 10⁻¹¹ can appear only as a decimal such as 0.0000000000667, never as 6.67e-11); and the IR has no operator for a square root, a power or a trigonometric function. For STEM subjects the translator is also told the following. These are instructions to the model; no code checks them, so a translation may not follow them:
  - to write every number exactly, expanding scientific notation exactly: 6.67 × 10⁻¹¹ as 0.0000000000667 and 3.0 × 10⁸ as 300000000 (a number the answer states in no spelling the checks read is named by them, OVS-TRN-005: Inspection I91);
  - to put the values the answer states in place of the symbols they bind, so a line of working becomes arithmetic on numbers;
  - to use one symbol per quantity, prefixed with the claim it comes from (g in claim s2.1 as s2_1_g), so the symbols of two claims never meet by accident;
  - the translator is told to record a unit as an assumption, never inside an expression: a unit is in words, in a symbol's `meaning`, an assertion's `label`, the problem's `notes`, the `interpretation`'s `reading` or `glossary`, or under a grounding of kind `assumption`; the engine checks numbers, never units;
  - to encode a square root or a trigonometric value as a comparison of squares, or to report the claim UNSUPPORTED.

  A translation that departs from these instructions is no fault for that alone: a symbol not prefixed with its claim, or a stated value left as a symbol, changes nothing by itself. Judge what it encodes (Inspection I78, I90 to I97): one symbol standing for two quantities, or a stated value left free so that the encoding says less than the claim, is `translation_unfaithful`.

  The translator is told nothing about tolerances or enclosures. The description of the subject it is given says that the formal check decides the written arithmetic, substitutions, unit conversions and dimension consistency "under the STEM tolerance rule", that the translator's own formalisations "add propositional structure and exact arithmetic on given values but do not check units", that the check can never establish "significant-figure policy", and, for Mathematics: Analysis and Approaches, "transcendental identities beyond exact values and 10^-15 enclosures". The tolerance rule and the enclosures belong to the branch's own checks (D31). How a translation encodes a stated precision, a rounded value or a constant such as π is the translator's own choice: judge what it encodes (Inspection I93).
- **D31 A STEM formal check.** These branches check the answer's own relations themselves, with no model. They check the relations below, one kind to a bullet, each with the readings it applies; where a named rule reads a relation, its check's `detail` names that rule ("rule part-value"):

  - **a statistic** stated for the values the prose lists ("The median of 18, 27, 40, 58, 80, 92 and 61 is 61.", "Median of 18, 27, 40, 58, 80, 92 and 61 = 61", "Mean of 18, 27 and 40 = 28.3") or for the supplied table's column its words name, with no row named ("Median uptake = 61 mm³ per g per hour", "The median uptake is 61 mm³ per g per hour."): the branch forms the median (the middle value in order, or the mean of the middle two), the mode (the one value that occurs most often, more than once), the range (the largest minus the smallest) or the mean (the sum over the count) of those values as written and sets the stated value against it, at severity warning (which values the statistic is of is a reading), its `detail` saying "formed by the STEM pack" and "rule statistics": the three medians of 61 fail (the median is 58);
    - a standard deviation, a variance, a quartile, a percentile, an interquartile range, and a mode the values do not have as one value, are named ST-UNDEC-001, unchecked;
  - the "show that" target, chemical equations, Boolean identities;
  - a Boolean expression evaluated under the values the answer gives its inputs ("With A = 1 and B = 0, NOT A OR B = 0" is decided at A = 1 and B = 0; the values are those its statement gives, or an earlier statement that sets them up: "Let A = 1 and B = 0. Then NOT A OR B = 0"; an input given no value must hold for each of its values);
  - **number bases**:
    - a whole number the prose restates right after it in another base, each base written, against the numeral read in its base ("The binary number 110010₂ is 48 in denary." fails, 50; "110010 in binary is 48 in denary", "The denary number 50 is 110011 in binary", "The binary representation of 50 is 110011" and "In hexadecimal, 2F₁₆ is 45 in denary" fail); a base named only right after the first numeral is read both ways, the first numeral's own or the base the second writes it in, and the check holds when either reading does ("10 in binary is 1010" and "1010 in binary is 10" hold, "10 in binary is 1011" fails), its `detail` saying "rule prose-base";
    - a base phrase opening the clause names the restated value's base the same way ("In binary, 1000 is 1111101100." fails, 1111101000; "In base 2, 13 is 1101." holds), read the same way with no comma and before "the number" ("In binary 1000 is 1111101000." and "In octal 64 is 100." hold, "In hexadecimal, the number 1000 is 3E9." fails); a numeral with a base marker keeps its own base, so the phrase names the base of the numeral that carries that base's marker ("In hexadecimal, 1000 is 3E9₁₆." fails, 3E8₁₆);
    - in a computer-science answer, a hexadecimal numeral written with letter digits ("3E8", "FF", "1F4") is read in base 16 where the words beside it, or a base phrase opening the clause, name base 16 for it, and never where nothing names its base ("255 is FF." is not read): "In hexadecimal, 1000 is 3E9.", "In base 16, 1000 is 3E9.", "1000 in denary is 3E9 in hexadecimal.", "The hexadecimal number 3E9 is 1000 in denary." and "In hexadecimal, 255 is FE." fail, "In hexadecimal, 255 is FF." holds;
    - a numeral set equal with "=" to one whose base the words right after it name is a base conversion, never written arithmetic ("1000 = 3E8 in hexadecimal.", "1000 = 1111101000 in binary." and "255 = FF in hexadecimal." hold, "1000 = 3E9 in hexadecimal." fails), its `detail` saying "rule prose-base";
  - **truth tables** (each written in AND, OR, NOT and XOR: the words, ∧, ∨, ¬, ⊕, "·", "+", letters written together, a prime or an overline; and in the gates NAND, NOR and XNOR, also written ↑ or ⊼ for NAND and ↓ or ⊽ for NOR, each the negation of AND, OR or XOR, NOT binding tighter than every one: "With A = 0 and B = 1, A NAND B = 1" holds and "With A = 0 and B = 0, A NOR B = 0" fails, "A NOR B = NOT (A OR B)" holds and "A NOR B = NOT A OR NOT B" fails; a gate written beside another operator, or two NAND or two NOR, with no brackets has two readings and is named ST-PARSE-002, never read one way: "A NAND B NAND C = 1", "A NAND B AND C = 0") and number bases.

  Each one is an entry of the receipt's `formal_checks`. Its `detail` says what it checks and which status it expects:
  - most say "expected ENTAILED";
  - "expected SATISFIABLE": some admissible reading of the answer's numbers gives the stated value. It never means that the value is true;
  - "expected UNSATISFIABLE": a Boolean identity, checked over its negation: no assignment makes its two sides differ; or a Boolean evaluation (its `detail` says "the Boolean evaluation" and names the values it is evaluated under), checked over its negation under those values.
  
  What the Given and table checks read, exactly:
  - **A Given value** is a symbol or a named quantity given a number with "=" in a statement that begins "Given", "Data", "Known" or "We know", or in the list a line "Given:" opens; or a value the prose of such a statement gives a quantity (rule prose-given): every value of a statement whose head ends with a colon within three more words ("Data: emf 15 V, internal resistance 0.50 Ω.", "Given: the mass of seeds is 12 g.", "Given: mass of seeds: 12 g.", "Given: 15.0 cm³ of acid.", "Known: the acid is 2.0 mol dm⁻³.", "Known values: …") and of the list a line "Given:" opens ("- mass of seeds 10 g"), and in a statement that begins "Given", "Known" or "We know" with no such colon, the values of its first clause, up to the first comma, semicolon or colon ("We know the mass of seeds was 10 g."; in "Given that the emf is 12 V, the current is 4.1 A." only the emf is a Given: the current is the statement's own result).
    - "Data" with no colon heads no Given clause ("Data analysis rewards …"). A prose Given is named by the words of its item, from the last comma, semicolon, colon, bracket or "and" before it, the words that open the statement or join the name to the value left out ("emf", "internal resistance", "mass of seeds"; after a copula, the words after it: "each value is the mean of 4 repeats" names the mean), or by the words after it when it comes first ("15.0 cm³ of acid" names the acid); a value right after "at", "when", "whenever" or "if" is the condition another value of the item is stated under, never a Given; an uncertainty written "±0.5 °C" or "+/-0.5 °C" in prose takes the unit written after it.
    - It is read as the same Given written with "=" and set against the request as below, except that when the request names a quantity by words that all stand in the Given's name, the Given is set against that quantity's value (rule named-given: "Data: emf 12 V, internal resistance 6.0 Ω." fails against the internal resistance 0.50 ohm, though the request states a 6.0 ohm resistor); its check's `detail` says "rule prose-given". An amount after a currency sign and a numeral written with a thousands space are never read in part (below).
    - On a report that answers a request, each one is set against the request's value of the same symbol when the request states one, and otherwise against the request's values of its kind: for a Given with a unit, the request's quantities of the same dimension, with those a text supplied with the request states in its prose when the Given's name shares a word with the sentence that states them ("Given: volume of thiosulfate = 40.0 cm³" against "50.0 cm3 of … sodium thiosulfate solution"; an uncertainty such as "+/-0.5 °C" is no value); for one written with "%", "per cent" or "percent", the request's percentages; for one written with a word after it, the request's numbers written with the same word ("5000 euros" against "4000 euros", "6 years" against "5 years"); for a bare number (no unit, no per cent sign, no word after it), the request's number it equals.
    - A Given that names a row and a column of a supplied table ("Given: dissolved oxygen at C = 3.5 mg dm⁻³") is set against that cell. A Given stated under a condition ("Given: oxygen uptake at 30 °C = 80 mm³ per g per hour", "Given: the count rate at t = 8 h = 820 counts min⁻¹", "Given: at t = 8 h, C = 820 counts min⁻¹") is set against the supplied table's cell at the row its condition names, in the column its name names; when its name fits no single column ("time" beside three timed trials), against that row's cells of every column of its dimension, one of which it must match. The condition itself is no Given and binds nothing.
    - A Given restates its data as written, so every written digit of a whole number counts, its trailing zeros too (30 and 20 differ; the `detail` says "rule given-digits").
    - A Given named as an uncertainty (its name holds "uncertainty", "precision", "resolution" or "tolerance": "Given: thermometer uncertainty = 0.5 °C") or written as one ("Given: Δθ = ±0.5 °C") is no value of its quantity: it is set against the uncertainties the request and its supplied texts state, those of its dimension, or their percentages for one written with "%" ("Uncertainties: thermometer +/-0.5 °C", "+/-2%"; the `detail` says "rule given-uncertainty"), never against a value of its quantity. A Given written with its uncertainty ("Given: T = 20.0 ± 0.5 °C") is set against the request at its central value (rule central-value), and its uncertainty against the uncertainties the request and its supplied texts state of its kind when they state one (rule given-uncertainty; otherwise the uncertainty written with it is not read). A Given uncertainty written with "±", "+/-" or "%" ("Given: count rate uncertainty = ±3%" against "+/-2%") and a relative uncertainty written with a value ("1620 counts min⁻¹ ± 2%") are read the same way.
    - A Given written with its uncertainty after the part's formula of its symbol ("Given: ε = 12 ± 0.1 V" after "ε = I(R + r)") is a Given, never the formula evaluated at it.
    - A Given of a function's value ("Given: v(1) = 4 m s⁻¹.", "Given: v(1) = 4.") is set against the request's function at the Given's argument, a number however it is written ("v(1/2)", "v(−1)"): the request's "v(t) = 6t - 3t^2" gives 3 at t = 1, so both fail. It is compared in the unit the request states for the function's values ("Its velocity, v m s^-1"), in SI ("Given: v(1) = 300 cm s⁻¹." holds), and as written for a Given with no unit.
    - A Given function ("Given: v(t) = 6t − 2t².", "Given: v(t) = 4.", or "Given: v = 6t − 2t²." for the function's own symbol) is set against the request's function for every value of its variable, whatever the variable is called ("Given: v(x) = 6x − 3x²." holds). The Given of a function's value and the Given function each have a check of their own, at severity warning (that the Given restates the request's function is a reading), whose `detail` names rule given-function: a stem_arithmetic entry, "the request's function at the Given's argument, against the Given value", every written digit counting, or a stem_algebra entry, "the Given function against the request's function".
    - The value of f, g or h applied to a number is an application of the function the request or the answer defines, so its Given ("Given: f(2) = 6.") is checked as the written arithmetic of the application ("the written arithmetic: 'f(2) = 6'"), an error when it fails; where neither defines it, it is named ST-UNDEC-003 like any Given of a function the request does not define. A Given of a function's value is data: no relation a later line is a step from ("So v(2) = 6(2) − 3(2)² = 0" after "Given: v(1) = 3." is the line's arithmetic alone).
    - Which value of the request a Given restates is a reading, so a failed Given check is INT-SUBJ-004, a warning.
  - **A Given none of these reads** is named by ST-UNDEC-003 (D32), one finding per statement naming each such Given and why: a kind the request states no value of ("t = 5.0 s" where the request states no time; a supplied text that states one in no sentence holding a word of the Given's name, "C0 = 1600 counts min⁻¹" beside the supplied background), a Given stated under a condition with no supplied table to read the row of, a Given uncertainty where the request and its supplied texts state no uncertainty of its kind, a Given of a function's value or of a function the request does not define ("Given: a(t) = 6 − 4t.", "Given: a(1) = 0."), a Given of the value of a function the request defines at an argument that holds a symbol ("Given: v(t + 1) = 4 m s⁻¹.") or a unit ("v(1 s)"), or with a unit of which the request states none, or of another dimension, for the function's values, a Given function written with a unit or with symbols other than its variable (rule given-function), or a bare number the request does not state.
    - A bare number is never failed: it may be a conversion (0.036 for 3.6%, 12 for "monthly"). Two values are neither checked nor named: zero, a condition the request states in words ("from rest"), and a data-booklet constant written at the booklet's value (g = 9.81 m s⁻²).
    - A Given that may be a numeral written with a thousands space ("4 000") is ST-PARSE-001, never read in part; so is a Given in a maths span the branch cannot read whole ("Given: count rate at t = 0 h = 1620 ± 2% counts min⁻¹", a unit after a per cent sign): nothing of the span is read, its condition included. An amount written after a currency sign ("P = €4000", "$7052.99 − $5000 = $2052.99") is no number the branch reads: a Given or a relation written with one is neither checked nor named. A report with no request (a relay) sets no Given against anything.
  - **A value a line of working takes from a supplied table** is set against the cells of the rows the line names ("From A to C ..."), or, when it names none, the rows its part's question names, in the column they name, when the line takes as many different cells of that column as there are rows named: a mean of three rows in a part whose question names two is another computation, and is not read.
    - A value from another row fails it ("(9.6 − 6.1) ÷ 9.6 × 100" for the decrease from A to C, 6.1 being site B's): INT-SUBJ-004.
    - The column is the one the line's own words name when they name exactly one and the line takes a cell of it, whatever column its part's question names: in a part whose question names the dissolved oxygen, "The nitrate rise from site A to site D is (8.4 − 1.2) ÷ 1.2 × 100 = 600%." and "From A to D the nitrate falls by (8.4 − 4.1) ÷ 8.4 × 100 = 51.2%." fail, 8.4 being site B's nitrate (before, the line and the question named two columns and the line was read in none).
    - A number the working adds to or takes from the column's values that is none of them is read too (rule table-terms): when the line takes the cell of every named row but one and exactly one such number, that number is the row's value copied wrongly and is set against the row's cell ("t = 12 h: 568 − 20 = 548 ± 11 counts min⁻¹" against the 12 h row's 586, "(9.6 − 3.9) ÷ 9.6 × 100" against site C's 3.8); when it takes the cell of every named row, the number is set against the values the request and its supplied texts state for the column's quantity outside the table ("t = 24 h: 220 − 25 = 195 ± 4 counts min⁻¹" against the background of 20 counts per minute), unless the line computes a cell or such a value itself ("566 + 20 = 586") or the number is a stated percentage of the cell (a bound: "586 + 11.72").
    - Each is a warning, every written digit counting (INT-SUBJ-004: which value the number stands for is a reading); nothing is read when two numbers or two rows' values are unaccounted for, or for a factor ("Uptake at 30 °C = 2 × 41 = 82": only its arithmetic is checked).
    - A named row whose cell the line states as its own value is the row of its result, never a row the working takes a value from ("Uptake at 30 °C = 2 × 40 = 80", the 40 being the 20 °C row's).
    - The values a line takes from the repeats of the one row it names, its condition's row or else its part's question's (the columns a table writes one quantity in, repeated: "Time, trial 1 / s", "Time, trial 2 / s", "Time, trial 3 / s"), are read too (rule row-terms): in a sum or a difference that takes the row's repeats, a repeat of another row is set against the named row's repeats ("Mean time at 30.0 °C = (33.1 s + 17.6 s + 32.5 s) ÷ 3 = 27.7 s" fails, the 17.6 being the 40.0 °C row's), and a term that is no repeat of the row, when it is the only one and exactly one of the row's repeats is taken nowhere, is that repeat copied wrongly and is set against it ("Mean time at 30.0 °C = (33.1 s + 43.0 s + 32.5 s) ÷ 3 = 36.2 s" fails against trial 2's 34.0, its arithmetic holding), each a stem_given entry at severity warning, every written digit counting; the row's repeats taken in another order hold.
  - **A value the prose or a statement gives from a supplied table** (a change between two rows, a value at a row, "The uptake at 20 °C = 40 mm³ per g per hour") is set against the table's cells when the rows and the column are read unambiguously; nothing is planned otherwise.
    - A row is a site's letter ("Dissolved oxygen at site C = 3.8 mg dm⁻³", "At site C, dissolved oxygen is …", "nitrate at E (2.3 mg dm⁻³)", "… at C (2.0 km), where it reaches 3.8 mg dm⁻³", "site A has the least nitrate (1.2 mg dm⁻³)") or a number with the key column's unit ("the measured count rate at 8 h is 820 counts min⁻¹"); the column is the one every word of whose name the statement's phrase holds, or the one whose counted quantity it names (the words before "per": "mayfly nymphs" for "Mayfly nymphs per kick sample"); a value whose unit, or the unit written right after it, is of another dimension than the column's is not its value ("at C (2.0 km)"), and "The value at site C = 3.8 mg dm⁻³" names no column and is not read (rule row-value).
    - The value, its row and its column may stand in any order in the value's own clause, an adverb such as "only" or "about" before the value, the row a possessive or after "of": "Dissolved oxygen was 3.9 mg dm⁻³ at site C.", "At site C dissolved oxygen is 3.9 mg dm⁻³.", "Site C's dissolved oxygen is only 3.9 mg dm⁻³.", "The dissolved oxygen of site C is 3.9 mg dm⁻³." and "Dissolved oxygen at site C, 3.9 mg dm⁻³, is the lowest." fail against site C's 3.8, as do "Site A has 43 mayfly nymphs per kick sample.", "At site A, mayfly nymphs = 43.", "The mayfly nymphs at site A number 43.", "site A has the least nitrate (1.2 mg dm⁻³) and the most nymphs (43)" and "while site B has the most nitrate (8.4 mg dm⁻³) and only 7" against A's 34 and B's 9, each at severity warning (rule row-value).
    - A numbered row is read the same, its key written after the key's symbol too ("The detector gave a measured count rate of 568 counts min⁻¹ at 12 h.", "At 12 h, measured count rate = 568 counts min⁻¹.", "The measured count rate at t = 12 h is 568 counts min⁻¹." fail against 586), and columns whose names differ only by a number are told apart by it ("At 30.0 °C, trial 2 took 43.0 s." fails against 34.0).
    - Not read: a clause that compares or states a change, a range, a ratio or a share, and a value followed by a comparison or an operation ("Dissolved oxygen at site C is 5.8 mg dm⁻³ lower than at A.", "Nitrate at B is 7 times that at A."); a processed quantity the column's name does not name ("The corrected count rate at 12 h is 566 counts min⁻¹.", "… after correction", "the mean …", "the uncertainty in …"); another quantity, named by a word that is not in the column's name before the word it shares with it ("The decay rate at 12 h is 0.087 h⁻¹." for "Measured count rate"); and a value stated under a condition, a hypothesis, a target or a modal verb, or after a bound ("If nitrate at site B fell to 4.0 mg dm⁻³, …", "A target of 9.0 mg dm⁻³ of dissolved oxygen at site C would …", "is below 4.0 mg dm⁻³"): each had been set against the cell and failed.
    - The words that choose the column, for a value at a row or a change between rows, are the value's own statement's: a sentence before it that names another column no longer leaves it unread ("It targets the largest rise in nitrate, from 1.2 mg dm⁻³ at A to 6.1 mg dm⁻³ at B" after a sentence naming the dissolved oxygen fails, 8.4).
    - When the stated value and the column's header both carry a unit of one dimension, they are compared in SI, so a table value restated in another unit fails ("from 18 cm³ per g per hour at 10 °C" for the table's 18 mm3 per g per hour). A header unit written with ASCII exponents ("mm3", "mg dm-3") is read as written with superscripts.
  - **A value a run computes under a condition, after a list or for a numbered item.** A maths run right after a condition word ("at", "when", "after", "before", "during", "within", "until", "for", "in") that opens with the condition and then computes the named quantity's value ("Mean time at 30.0 °C = (33.1 s + 34.0 s + 32.5 s) ÷ 3 = 33.2 s", "I at t = 5 s = 12 V / 4.5 Ω = 2.7 A", "Speed after 2.0 s = 9.8 m s⁻² × 2.0 s = 19.6 m s⁻¹", "Uptake at 30 °C = 2 × 40 = 80"), one right after the list or the range of values the prose names its quantity by ("Mean of 18, 27 and 40 = (18 + 27 + 40) ÷ 3 = 28.3", "The rise from 20.0 °C to 30.0 °C = 30.0 − 20.0 = 10.0 K"), and one for a numbered item ("Rate for trial 2 = 1/60.8 s = 0.0164 s⁻¹", "Year 2 = 4000 × 1.036² = 4293.18 euros") give the named quantity's value: the condition, the list's last value and the item's number are part of its name, never a side of a relation, and the computation's links are checked as in any chain (rules value-at, name-list and item-label; read as relations, "30.0 °C = (33.1 s + 34.0 s + 32.5 s) ÷ 3" and "40 = (18 + 27 + 40) ÷ 3" failed correct working, the first with ST-DIM-001).
    - When the computation takes exactly one value of the condition's dimension, that value is set against the condition, every written digit counting (rule condition-value: "The charge that flows after 2.0 s = 4.1 A × 3.0 s = 12.3 C" and "The energy dissipated in 10 s = 16.4 W × 20 s = 328 J" fail; a condition with no exact SI value, "at 30 °C", is set against nothing), and a term of a sum or a difference that takes the listed values and is none of them is set against the list (rule name-list: "Mean of 18, 27 and 40 = (18 + 27 + 41) ÷ 3 = 28.7" fails), each at severity warning: which value stands for the condition or for a listed value is a reading (INT-SUBJ-004).
    - The row of a supplied table that a run's condition names is the row of the run's result, never a row its working takes a value from, when the working takes a cell of the column and not that row's ("Uptake at 30 °C = 2 × 40 = 90": its arithmetic fails, and the 40 is not set against the 30 °C row).
    - A run that converts the condition itself ("at 25 °C = 298 K") is a conversion, as before. A list with no computation after it states a statistic of the listed values when a statistic names it ("Mean of 18, 27 and 40 = 28.3" holds and "Mean of 18, 27 and 40 = 29.3" fails: rule statistics, above), and is a relation written partly in words after any other name ("Sum of 18, 27 and 40 = 85": ST-PARSE-001).
  - **A law and the line that evaluates it.** A line that gives a symbol a value right after its part states a law for it, written so that no substitution pairs each of the law's symbols with a value and the law cannot be checked under its symbols' stated values ("V = ε + Ir", then "V = 12 V − (4.14 A × 0.50 Ω) = 9.9 V", ε having no stated value), is set against the law at the values the line puts in, each value written with a unit paired with the law's symbol of its dimension (known from the symbol's stated values or from the law itself: ε = 12 V, I = 4.14 A, r = 0.50 Ω): the law gives 14.07 V where the line states 9.9 V, so the check fails, its `detail` saying "the law stated in" its statement "at the values the line puts in" and "rule law-values", at severity warning (which value stands for which symbol is a reading: an INT-SUBJ-004 naming the law's claim and the line's), while the line's own arithmetic holds.
    - Written with the law the line follows ("V = ε − Ir"), the line is that law's substitution, read as before.
    - Nothing is planned when the line's values with units do not stand one for each symbol ("V = 12 V − 2.07 V = 9.93 V"), when no pairing agrees with the dimensions or two pairings give different values, or when the law stands in another part; a line that takes a value of a dimension no symbol of the formula has, nor a power of one, evaluates another relation and is not set against the formula ("P = 9.93 V × 1.655 A = 16.4 W" right after "P = V²/R").
    - A failed substitution names the claim that states the law it evaluates beside the line's ("P = V/R", then "P = (9.93 V)² / 6.0 Ω = 16.4 W": its INT-SUBJ-001 names the law's claim, the line's and the one that states V).
  - **A processed value.** A line that processes one cell of a supplied table into another value of its quantity ("t = 0 h: 1620 − 20 = 1600 ± 32 counts min⁻¹") states the processed value of that row.
    - A line of a later part whose question, or the line itself, names the processed quantity by the word that sets it apart from the column ("corrected") and that takes the raw cell instead is set against the processed value: INT-SUBJ-004 when it differs.
    - A line of the processing part itself, a part that names no such word,
      - a line that processes the raw cell again into the processed value ("C₀ = 1620 − 20 = 1600 counts min⁻¹"),
      - a line that takes a percentage of the raw cell (written with "%", "±2% × 1620" too, as the decimal of a percentage the answer, the request or its supplied texts state, or as a division by a number N with 100/N such a percentage: "2% of 1620 is 0.02 × 1620 = 32.4 counts min⁻¹", the uncertainty of the measured value by the answer's own rule, "1620/50 = 32.4 counts min⁻¹", or in any other arithmetic form: "1620 × 2 ÷ 100 = 32.4 counts min⁻¹"),
      - a line that adds that percentage of the raw cell to it or takes it away, the bounds of the measured value ("1620 + 32.4 = 1652.4 counts min⁻¹", "1620 × 1.02 = 1652.4 counts min⁻¹"),
      - a line that processes the raw cell inside its own arithmetic ("C = (1620 − 20) × (1/2)⁴ = 100 counts min⁻¹"),
      - a line that computes a ratio of the raw cell to another value of its quantity or to its processed value, or sets a value over it ("1620/820 = 1.98", "1620/1600 = 1.0125", "32.4/1620 = 0.020"),
      - a line whose own words name the raw quantity by the word of the column's name that sets it apart from the processed one and not the processed quantity ("The measured rate fell by 1620 − 820 = 800 counts min⁻¹", "The mean of the first two measured rates is (1620 + 1151)/2"), and a line that computes a percentage or a ratio of the raw cell rather than a value of its quantity ("20/1620 × 100 = 1.2% of the first reading") are not read.
  - **Silence is not a check.** A claim with no `formal_checks` entry and no ST code was not checked: nothing the branch decided says it holds.
    - It states no relation the branch reads as a claim (a definition or a formula, a value given to a symbol outside a Given, a condition, an equation in a symbol the answer gives no value written with no quantity named before it as its value ("2x + 3 = 7"), an equation written with no quantity named before it as its value ("16.4 W = I² × 6.0 Ω" alone, "So 12 V × I = 60 W.", "The equation is 12 V × I = 60 W": an equation, an expression or a law is no quantity), one its part solves for one of its symbols ("The power is 16.4 W = I² × 6.0 Ω, so I = 1.65 A", "…, giving a current of 1.65 A") or one for a symbol whose stated values all stand in other parts about a result its part already states ("The power in it is I² × 6.0 Ω = 16.4 W") or giving the quantity its part asks for ("The power in the 6.0 Ω resistor is 9.93 V × I = 16.4 W."), a question left unanswered, words, amounts written after a currency sign, the value a change ends at that the prose computes itself: "the current falls from 4.1 A to 2.7 A" checks 4.1 A only, and a substitution stated after the change, in its statement or in its part may take 2.7 A as a value of the current's symbol, its check saying so: rule changed-value; one in an earlier part never does), or a Given of zero or a booklet constant.
    - What the branch reads and cannot check, it names: on a report that answers a request, a Given it cannot set against the request (ST-UNDEC-003); in any report, a chain that computes a quantity from a symbol with no stated value ("E = 0.5 × k × 0.04 = 1.0 J", or "The energy is 0.5 × k × 0.04 = 1.0 J." when its statement does not go on to solve it: ST-UNDEC-002; a "×" with a space before it and a symbol after it is a product, never the magnification "0.5×"; a symbol written applied to a value is a function only where the answer or the request defines it as one, "C(12)" after "C(x) = 40 + 2.5x", so "The energy is ½k(0.20)² = 1.0 J." names k, ST-UNDEC-002), a ratio set against a number ("The ratio of the resistances is 4.0 : 6.0 = 0.67.": ST-UNDEC-001), a statistic the branch does not form ("The standard deviation of 18, 27 and 40 is 9.0.": ST-UNDEC-001), a statement with a relation sign (=, ≈, ≠, ≤, ≥, ≡, <, >) between numbers or one-letter symbols that no maths span reads, and a relation written partly in words, "when 17 is divided by 5 = 2" (ST-PARSE-001), besides the relations D32 lists.

  `satisfied` is true when the result's status is the one the check expects, false for any other definitive status, and null for a non-result. On a STEM check, INCONSISTENT_PREMISES and a run marked "vacuous: E108" are null too. A failed check is INT-SUBJ-001 (error). A check whose `detail` says "failure severity warning" fails only under a reading the answer did not state (a rounding, a unit, the quantity a sentence names, the rows of a supplied table, which of two values a line means, the direction of a percentage change, the number of half-lives the prose states, which value an uncertainty rule's percentage is of), and is INT-SUBJ-004 (warning). An undecided check is INT-SUBJ-002 (warning). The finding of a failed substitution names the claims of its statement first, then, for each symbol it substitutes whose value one earlier statement alone states, that statement's claims (a value stated in part (c) that part (d) contradicts is named in both): its `claim_ids` may hold claims its `detail` does not quote.

  How to read one:
  - **Its `detail`.** It names the check's kind and claims ("stem_arithmetic in claim s1.4:"), quotes the statement checked ("the written arithmetic: '2.4 Ω + 0.50 Ω = 3.9 Ω'"), gives the tolerance rule in brackets, then the form, the policy and the readings, and ends with "solver" and the status of its signed result. "Form E (entailment, expected ENTAILED)" decides the statement on the values as written; "Form S (satisfiability, expected SATISFIABLE)" asks whether some admissible value of an interval makes it hold. "policy linear" or "nonlinear" names the engine policy it ran under. "readings: as written; SI" says it was decided on the values as written and again converted to SI by exact unit factors; "as written, per cent as a fraction" says a per cent taken of a number was also read as its fraction with the units as written ("1620 × 2% = 32.4 counts min⁻¹", "±2% × 1620 = ±32.4 counts min⁻¹"); "exact mode" says every operand and the stated value are exact.
  - **The tolerance rule.** A stated value S holds when |C − S| ≤ h + τ·|C|, C the value computed from the written expression. This is the rule the checks apply, and the bracketed short form in every `detail` says the same (its 1/100 for "=" is the most τ a check uses there: rule operand-precision may use less, and the `detail` then gives the τ it used):
    - h is half a unit in S's last written digit: 5.0 gives 0.05 and 1.20 × 10³ gives 5. The trailing zeros of a whole number written without a point count only up to the smallest number of significant figures among the expression's measured operands, so 1200 against two-figure operands gives 50, and 110 against the operands 80 and 40 gives 5, not 0.5. A value set against another value has no operands, so none of its trailing zeros count: in a conversion or a restatement, 600 gives 50.
    - When C is itself a stated value, h adds C's own half-width: in a conversion ("2.4 Ω = 0.0024 kΩ"), a substituted value w against a value b the answer states for its symbol (|w − b| ≤ h(b) + h(w)), and a restated result S against the chain's final value S′ (|S − S′| ≤ h(S) + h(S′)).
    - A value the request or a text supplied with it states, and a Given that restates one, is data, taken as written: a Given value, or a value substituted for it, matches it only when one of the two is the other rounded to its own last written digit, |w − b| ≤ max(h(w), h(b)), the `detail` saying "rule given-data": "Given: r = 0.49 Ω." and "Given: r = 3.7%." fail against the request's 0.50 ohm and 3.6% (two roundings of one value, 0.495, are no restatement of the data), "Given: r = 0.5 Ω." and "Given: g = 9.81 m s⁻²." for the request's 9.8 hold, and "2.1 kg" substituted for the request's m = 2.0 kg fails.
    - A rounding the prose states for a restated value ("To the nearest whole number, the decrease is 60%", "60%, to 2 s.f.") gives its h and says which zeros of a whole number count: 1/2 for the nearest whole number and for 60 to two significant figures, 5 for 60 to one. It never gives less than half a unit in the value's last written digit, and the value is also written to the place the rounding names: a check of its own, rule rounded-digits (above), sets that place against the place of the value's last written digit, exactly. A rounding a line states for its own result, after it or opening its clause before it ("(92 − 61) ÷ 92 × 100 = 34% to 2 s.f.", "To 2 s.f., 1000 ÷ 3 = 330."), gives that result's h the same way (rule result-rounding: "= 33% to 2 s.f." fails, 33.7); a rounding that closes an earlier value's restatement ("so 5902 euros to the nearest euro, and …") is that value's, never the next chain's.
    - A value restated with a rounding the prose states to the place the value it restates is written to (the same h) must equal it: h is 0, and the `detail` says "rule same-place" ("To 3 s.f., P = 16.5 W" after "= 16.4 W" fails, "To 2 s.f., P = 16 W" holds). With no rounding stated, h(S) + h(S′) bands it as above ("Therefore the decrease is 60.5%" after "= 60.4%" holds).
    - A value restated with a rounding the prose states that is finer than the place the chain's final value is written to states figures that value does not carry, so it has a second check, rule finer-restatement, at severity warning: it is set against the value the expression the chain's last "=" evaluates gives, read as written arithmetic is (its numerals as written; a carried result or a constant ranges over its interval, below), with h the stated rounding's alone (never less than half a unit in the restated value's last written digit) and τ 0, since that the restated figures are the line's arithmetic as written is a reading the answer did not state. After "V = 12 V − (4.14 A × 0.50 Ω) = 9.9 V", "To 3 s.f., V = 9.90 V." and "To three significant figures, V = 9.94 V." hold against 9.9 V and fail this check (the arithmetic gives 9.93), INT-SUBJ-004, while "To 3 s.f., V = 9.93 V." holds both; a rounding no finer than the final value's place ("To 2 s.f., V = 9.9 V.") has no such check.
    - τ is 1/20 for a relation written "≈", "≃" or "~", or after "approximately", "about", "roughly" or "estimate", whatever the check: a conversion written "≈" gets 1/20 too. A restated result is the one exception: a value the prose restates after one of these words ("= 2.67 A, which is about 2.7 A", "Therefore the decrease is about 60%.") is the restated value rounded, so its τ is 0, as for every restated result, and its `detail` says "τ = 0". Otherwise τ is 1/100 for "=" in written arithmetic, and 0 for unit conversions, comparisons, substitutions, restated results, Given values, roots, "show that" targets and exact work (every operand and S exact: then h is 0 too, unless S closes rational written arithmetic with two or more significant figures, the next point).
    - When every operand of a line written "=" is a written numeral (no carried result, constant, symbol or function value), τ is at most twice the largest relative change the rounding of those numerals can make to the computed value (rule operand-precision): "4000 × 1.036³ = 4467.74" fails, 0.45% being beyond the 0.29% the rounding of 1.036 allows, and "586 − 20 = 564 ± 12" fails, whole numbers being exact (τ = 0). A stated value that is a whole number ending in zero, written without a point, keeps 1/100. The `detail` gives the τ used.
    - Exact work whose stated value S, of two or more significant figures, closes rational written arithmetic has h half a unit in S's last written digit, every trailing zero counting (rule exact-rounding): a whole computed value is stated exactly, "17 × 23 = 392" and "1000 ÷ 3 = 330" fail, and one that is not whole may be stated to S's last digit, "(92 − 18) ÷ 18 × 100 = 411%" and "1,000 ÷ 3 = 333" hold, while "7/3 = 2" fails, a single figure showing no rounding.
    - A numeral that writes a value the request states is the request's data, exact, never rounded, a per cent's decimal and the factors 1 ± it included (3.6% gives 0.036, 1.036 and 0.964; rule operand-precision): "4000(1.036)^{12} = 6141.73" fails, 0.44% under 1/100 (6114.73), "Also (12 V)² / 4.0 Ω = 36.3 W." fails (36), and "4000 × 1.036⁵ = 4773.7406" fails in its fourth decimal (4773.7401); a stated side that is itself an expression of rounded numerals carries their rounding ("1/4.0 Ω + 1/6.0 Ω = 0.250 Ω⁻¹ + 0.167 Ω⁻¹" holds).
    - A value the prose takes from a table supplied with the request (a cell, or the change between two rows) is set against the table's cells taken as written: only h(S) bands it.
    - A stated value written with its uncertainty, S ± u ("586 − 20 = 566 ± 12"), is checked at its central value S under this rule: u never widens h, so a slip within the uncertainty fails ("586 − 20 = 556 ± 12"), and this rule does not check u itself. The `detail` says so ("rule central-value"). When the answer states how it obtains its uncertainties as a percentage of a value it names ("each corrected value has an absolute uncertainty of 2% of the measured value"), u is set against that percentage of the one cell of the supplied table's column the line takes ("1151 − 20 = 1131 ± 23": 2% of 1151 is 23.02), only u's own half-width banding it, at warning severity (rule stated-uncertainty); otherwise u is not checked.
    - A rounded result the answer carries forward, a constant it quotes at the data booklet's precision, π, e and the value of a function range over an interval: π, e and function values over enclosures no wider than 10⁻¹⁵·max(1, |value|), so an enclosure never fails correct work. A result of exact working the answer carries forward ("T = ln 2 ÷ ((ln 2)/8) = 8": every operand and the stated value exact) is carried exactly, with no interval (rule exact-carry): "8 ln 2 ÷ ln(1568/816) ≈ 9.5 h" fails (8.49).
    
    So '(80 − 40) ÷ 40 × 100 ≈ 110%' holds: C is 100, h is 5 (110 against 80 and 40) and τ is 1/20, a band of 5 + 5 = 10 that reaches 110. Read h and τ from the `detail` ("τ = 1/100", "exact mode") and the result's `problem`, never from a rule of thumb.
  - **Its result.** The `problem` of `/results/<formal_result_id>` names the value computed from the written expression (`C_DEF`: c) and the stated value (`R`: r), one pair per reading (`C_DEF_1`, `R_1`, ...), and its conclusion `STATED` is the band. A failed check with one reading gives the engine's values in its finding: "(engine counterexample: c = 29/10, r = 39/10; c is the value computed from the written expression, r the stated value)". Read c and r there or in the problem; never recompute the arithmetic to overrule the signed status.
- **D32 ST codes.** The science, mathematics and computer science branches report what their checks could not decide, or decided under a limitation, as `ST-*` entries of `structural_findings`, each naming the claims of its statement. Three say more: ST-DIM-001, ST-DIM-002 and ST-UNDEF-001 say that a relation is wrong as written (its two sides have different dimensions, a sum adds unlike quantities, an expression is undefined), which the branch decides with its own unit arithmetic or domain rule, with no engine check. None is an error: a warning makes the receipt ACCEPTED_WITH_FINDINGS, an info changes nothing, and the report is delivered either way. A failed check is never an ST code: it is INT-SUBJ-001 or INT-SUBJ-004 (D31).

  | Code | Severity | What it says |
  | --- | --- | --- |
  | ST-PARSE-001 | warning | a maths span uses notation outside the branch's grammar, a relation is written partly in words ("the remainder when 17 is divided by 5 = 2"), a relation sign stands between maths that no span reads ("17 % 5 = 2" outside computer science), or a Given may be a numeral written with a thousands space ("4 000"); its relations are not checked, and a Given in such a span is not read in part |
  | ST-PARSE-002 | warning | an expression has too many readings (an implicit multiplication, a unit or a symbol that can be read two ways, or a NAND, NOR or XNOR written beside another operator, or two NAND or two NOR, with no brackets: "A NAND B NAND C = 1"); it is not checked |
  | ST-UNDEC-001 | warning | a relation outside the encodings, for example a derivative of what is no polynomial the answer or the request defines, or set equal to a number where it is no constant (the paragraph after this table), an integral, a limit, a sum Σ over a symbolic bound or of more than 24 terms (a sum over written whole-number bounds is expanded and checked as arithmetic: D31), a product ∏, an ellipsis written in LaTeX (`4787.58\ldots`, `1 + 2 + \cdots + 10`), a vector, a factorial, a binomial coefficient or a permutation count such as ⁵C₂, 5C2, nCr or C(5, 2), an integer power beyond 12, a symbolic power, a function of an unknown, an approximation step, an integer remainder or quotient of a negative number, of a number that is not whole, or by a divisor that is not a positive whole number, a statistic the branch does not form (a standard deviation, a variance, a quartile, a percentile, an interquartile range, or a mode the values do not have as one value: rule statistics, D31), a ratio set against a number ("4.0 : 6.0 = 0.67"); the reason is named and the relation is not checked |
  | ST-UNDEC-002 | warning | a numeric relation depends on a symbol with no stated value ("E = 0.5 × k × 0.04 = 1.0 J", "The energy is 0.5 × k × 0.04 = 1.0 J."); it is not checked |
  | ST-UNDEC-003 | warning | a Given value could not be set against the request (D31): the request states no value of its kind (for a Given uncertainty, no uncertainty of its kind) and no supplied table names it, or it is a bare number the request does not state; or it is a Given of a function's value or of a function that the request does not define, or that cannot be set against the request's function: an argument that holds a symbol or a unit, a unit for the function's values the request does not state, a Given function written with a unit or with symbols other than its variable (rule given-function, D31: "Given: a(t) = 6 − 4t."); each such Given of the statement is named with why, and none is checked against the request |

  | ST-UNIT-001 | warning | a unit is not recognised; the relation is checked as written only, at warning severity |
  | ST-UNIT-002 | info | a unit symbol with two readings (M: molar or mega) is checked under both |
  | ST-DIM-001 | warning | the two sides of a stated relation have different dimensions, so the relation is wrong as written; a bare number beside a quantity counts as a pure factor unless the answer substitutes it for a symbol, states its value with a unit elsewhere or writes a data-booklet constant ("0.693 × 8.0 h = 5.5 h⁻¹": h against h⁻¹). A unit written right after a fraction whose slash has no space on either side ("1/40 s⁻¹", "(ln 2)/8 h⁻¹") is the divisor's or the whole fraction's: the relation is read, and checked, with the fraction's own unit when that gives its two sides one dimension and the divisor's does not ("k = (ln 2)/8 h⁻¹ = 0.0866 h⁻¹", "The rate is 1/40 s⁻¹ = 0.025 s⁻¹": no finding, the check's `detail` naming rule fraction-unit), so ST-DIM-001 is raised only when neither reading agrees ("1/40 s⁻¹ = 0.025 m"); with a space around the slash ("1 / 0.087 h⁻¹ = 11.5 h⁻¹") or with ÷ the unit is the divisor's.   | ST-ALG-001 | warning | a step takes only the non-negative square root and states no domain, or, in mathematics, a line evaluates a law solved for a squared symbol (rule solved-law, D31: "A = πr²" then "r = √(50/π) = 3.99") and states none; the algebra, or the substitution, is checked under that condition |
  | ST-CHEM-001 | warning | a chemical equation cannot be read; its balance is not checked |
  | ST-CODE-001 | info | a code block is present; code is never run or checked |
  | ST-SCOPE-001 | info | a symbol is given another value later in the answer; a substitution may match either |
  | ST-LIM-001 | warning | an expression or a number exceeds a bound of the checks; it is not checked |
  | ST-LIM-002 | warning | more relations or maths spans than one report's checks take; the count and the first left unchecked are named |
  | ST-INTERNAL-001 | warning | the branch's checks failed internally; the checks it names are missing, never passed |

  A derivative is read in Leibniz notation of any order ("dN/dt", "dθ/dt", `\frac{dN}{dt}`, "d/dx (sin x)") or as a letter with primes written applied to a bracket ("θ′(t)"), rules leibniz and prime-derivative. A polynomial's derivative is checked (rule derivative, D31), unless it is set equal to a number where it is no constant ("dv/dt = 6" for v(t) = 6t − 3t², an equation in the variable to solve); a derivative of anything else is ST-UNDEC-001. A derivative's value at a point is set against a formula the answer states for that derivative, so "v'(1) = 6 + 6(1) = 12" after "v'(t) = 6 − 6t" fails; a primed letter with no bracket, "v' = 2.0 m s⁻¹", is a symbol.

  Two of ST-UNDEC-001's constructs are checked where D31 reads them: a definite integral of a polynomial in one variable with whole-number limits, and its evaluation bracket ("∫₀¹ 6t dt = [3t²]₀¹ = 3", rule definite-integral), and a decimal written with its digits cut, in LaTeX or as "2.66…" or "2.66...", set equal or approximately equal to a closed expression on either side or restated as a value, in a relation that holds no other construct outside the encodings ("8/3 = 2.66…", "0.333… = 1/3", "= 4787.58…" then "= 4788 euros, to the nearest euro", rule ellipsis-rounding). Every other integral and ellipsis (a cut value inside an expression, "0.333… × 3 = 1", or set equal to a symbol, "x = 2.66…"), and a cut value after a power beyond 12, stays ST-UNDEC-001.

  The infrastructure re-derives every ST code and every check's statement from the journaled report, its request and the signed results: an ST code the receipt dropped or moved to another claim is OVS-RCPT-004 (an ST-UNDEC-003 dropped from a Given included, so that the Given would read as checked), one the branch does not give is OVS-RCPT-005, a check the branch derives that the receipt does not carry is OVS-FORM-004, and a check whose `detail`, claims or failure finding are not the check's and its result's is OVS-RCPT-007 (Inspection I98).
